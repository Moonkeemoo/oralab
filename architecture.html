01North star

"Least problems in LIVE, nothing gets stuck." Every design choice passes through this filter. Enemies: orphaned positions, phantom closures, stuck orders, false SL fires, drift between local state and chain truth, untyped errors that disappear silently, any path that bypasses decide_exit.
Product north star (added post-review): alpha capture starts week 4, not week 8. Every week of pure planning past week 1 is foregone alpha. Sports-focused, sports-first, sports-only in P1.

Goals

  • P1 (weeks 1–3): solo bot, sports-only, on CLOB V2, production-quality
  • P1.5 (week 4): minimal SportsScoreReactor — alpha capture starts here
  • DB-first state model (Postgres from Day 1) — no JSON files as truth
  • 10 V2 invariants enforced as failing tests before code (from SPEC.md)
  • decide_exit as a pure function — single source of exit truth
  • Observability stack from Day 1 — OTEL + Prometheus + Loki + Grafana

  • Telegram Mini App as primary UI (Caddy /api route, no web dashboard)
  • Strategy pattern — vertical isolation, validated early via SportsScoreReactor
  • Continuous on-chain reconciliation with explicit eventual-consistency grace periods
  • Non-custodial primary (BYO smart wallet via ERC-1271), custodial opt-in P3c+
  • Builder rewards registered + populated from Day 1 (sized in week-1 spike)

Non-goals

  • Multi-user, BYO wallet, custodial in P1 (deferred to P3c after solo LIVE proven 14d)

  • Web dashboard (Mini App only — no Caddy basic auth, no Flask)
  • Trading platforms beyond Polymarket
  • Custom matching engine, market making, automated arbitrage routing
  • Blank-slate rewrite without referencing v1 wisdom
  • Dropping v1 LIVE before v2 has parity in DRY parallel run (7-day hard gate)
  • SQLite or any single-writer DB (Postgres from Day 1)
  • Bun in P1 production (Node 22 LTS first; Bun as P5+ optimization)
  • Ukrainian platform UI / i18n in code (Claude↔Taras stays Ukrainian — that's separate)
  • Python in trading hot path (calibrator service may stay Python — out of hot path)
  • US-region operations until lawyer review (CFTC Polymarket precedent)
  • Multi-user push without pricing validation waitlist signal

07The 10 V2 invariants (constitution)

Distilled from 31 v1 invariants + 4 months of bug-fix experience. Source: docs/rewrite/SPEC.md. Each is a failing test in v2 before any code is written. Watchdog rules backstop them at runtime. P3c multi-user: M1 / M4 / D3 become per-user.

Money-safety (5)

INV-M1Never sell more than on-chain shares.
Pre-flight balance check via /positions or getBalanceAllowance. order.size = min(intent.size, free, on_chain). R21 backstop.
INV-M2Never sell below outcome floor.
floor = max(min_tick, expected_outcome_value × 0.3). R22 backstop.
INV-M3Closure ONLY via on-chain SELL fill OR UMA-resolved.
Two paths only: /activity shows our SELL with tx hash, or market.umaResolutionStatus === "resolved". closure_reason never written before fill confirmation (QA-181).
INV-M4Atomic budget transaction.
Position update + entry-cost + exited-flag → single Postgres transaction. Crash mid-update → next-startup reconciliation detects delta. R9 backstop.
INV-M5Never double-act on same trade.
VALID_TRANSITIONS enforced. EXITING → EXITING forbidden. Every exit_executor call: if state !== "exiting" return.

Data correctness (3)

INV-D1Source-of-truth hierarchy, never otherwise.
/positions = position truth. /activity = realized PnL truth. gamma.outcomePrices = odds truth. /book = bid/ask truth (NEVER /midpoint, NEVER mark*0.99 synthesis). All log/Telegram messages labeled "verified" or "local-only".
INV-D2Mark staleness gate before SL/TP fires.
decide_exit returns HOLD if mark_age_s > 60 OR bid <= 0 OR ask >= 1 OR spread/midpoint > 50%. Post-fill 5s debounce (QA-165). Spread gate uses real /book (QA-180).
INV-D3Continuous reconciliation with explicit grace periods.
Position monitor 2Hz tick reconciles DB vs /positions. Eventual consistency expected — see reconciliation algorithm in section 08.

Operational (2)

INV-O1Circuit breaker on SDK calls.
Health check every 30s. >2 consecutive fails → block new entries; existing exits via emergency path with accept_loss=true.
INV-O2Bounded operations: timeout + retry + idempotency.
Every HTTP/RPC: timeout=5s, retry 3× with exponential backoff. Order placement idempotent via client_order_id. Cancel idempotent (404 = OK if expired).

08Trading core — decide_exit, ExitIntent, state machine, reconciliation algorithm

decide_exit — pure function

type ExitAction =
  | "hold"           // do nothing this tick
  | "sell_bid_probe" // GTD@bid+1tick, 60s — first attempt
  | "sell_bid_aggr"  // GTD@bid-1tick, 60s — eat spread (post-sweep)
  | "sell_fok"       // FOK at any price >= floor — last resort
  | "redeem"         // market resolved; CTF redeemPositions
  | "freeze";        // reconciliation conflict; halt action

interface ExitIntent {
  action: ExitAction;
  price: number;
  size: number;
  urgency: 1 | 2 | 3 | 4 | 5;
  reason: string;
  gates: string[];        // invariant IDs that fired (audit)
  snapshotTs: number;
}

// Pure. No I/O. ExitExecutor is the ONLY thing that mutates state.
function decide_exit(
  pos: PositionView,         // immutable view
  snap: MarketSnapshot,      // validated mark + real bid/ask from /book
  cfg: ExitConfig,           // TP/SL/trailing thresholds
): ExitIntent;

Reconciliation algorithm (per-tick, expanded INV-D3)

async function reconcile_position(pos: Position, now: number): Promise<ReconResult> {
  const chain = await polymarket.getPositions({user: pos.wallet});
  const chain_pos = chain.find(p => p.asset === pos.asset);
  const age_s = (now - pos.last_state_change_ts) / 1000;

  // Case 1: chain has nothing for this asset
  if (!chain_pos) {
    if (pos.status === "PENDING" && age_s < 30) return {action: "continue"};
    if (pos.status === "FILLED" && age_s < 30) return {action: "continue"};
    if (pos.status === "EXITING" && age_s < 60) return {action: "continue"};

    // Beyond grace — chain says "no position"
    if (pos.status === "EXITING" && await activity.findOurSell(pos)) {
      return {action: "close", reason: "sell_filled_chain_lag"};
    }
    // OPEN with no chain backing after 30s — phantom
    log("CRITICAL", "position vanished from chain", pos);
    return {action: "freeze", reason: "chain_invisible"};
  }

  // Case 2: chain shows position; check size convergence
  const drift = Math.abs(chain_pos.size - pos.shares) / pos.shares;

  if (drift < 0.005) {
    return {action: "ok", chain_size: chain_pos.size};
  }

  // Eventual consistency window (5-30s after our state change)
  if (age_s < 30) {
    return {action: "continue", note: "grace_period"};
  }

  // Sustained drift — three thresholds
  if (drift < 0.05) {
    log("WARN", "minor drift", {drift, pos});
    return {action: "sync_to_chain", new_size: chain_pos.size};
  }
  if (drift < 0.10) {
    log("P1", "meaningful drift", {drift, pos});
    return {action: "freeze", reason: "drift_5_to_10"};
  }
  // drift >= 10%
  log("P0", "major drift", {drift, pos});
  return {action: "freeze", reason: "drift_over_10"};
}

Recovery from FROZEN: human-only via Mini App "Resume" button. Operator confirms current chain state matches expectation. System resyncs DB to chain, allows resume to OPEN. No automatic recovery — frozen-then-broken would compound the issue.

Position state machine — 7 states

PENDING ──→ FILLED ──→ OPEN ──→ EXITING ──→ CLOSED
                            │
                            ↓
                        RESOLVED ──→ CLOSED
                            ↑
PENDING ──→ FAILED ──→ FILLED   (ghost recovery path)
                  └──→ CLOSED
EXITING ──→ OPEN                (sell retry rollback)
OPEN/EXITING ──→ FROZEN         (reconciliation conflict; manual recovery)

11Wallet models — non-custodial primary

P1 Solo (Taras, env)

Single env-driven private key, signature-type 1 (proxy/funder). Same as v1. wallets table has one row id=1; users.wallet_mode = "env". No encryption, no key rotation, no per-user logic. Schema is multi-user-shaped but only one user exists.

P3c primary BYO (smart wallet)

User connects their own EOA via Telegram WebApp (or external WC). User deploys Safe / AA wallet with our backend signer key as delegated signer via ERC-1271. We sign orders on their behalf. User retains full custody — can revoke our signer at any time. Lower legal exposure, cleaner UX. Default option in P3c.

P3c opt-in Custodial (Polycop-style)

User explicitly opts in. We generate EOA, store encrypted PK with KMS-style master key (Vault on Hetzner second box, or external AWS/GCP KMS). Trade on user's behalf. Audit log of every signing op (append-only, replicated to cold storage). Withdrawal 2FA via Telegram. Higher security/legal burden — see Multi-user security section.

Why non-custodial primary: custodial = MiCA/BSA territory. BYO via ERC-1271 means we're software-as-a-service on top of user's own funds, not a custodian. Legal exposure dramatically lower. Pricing later may differentiate (e.g., free for BYO, fee-share for custodial — convenience tax).

Activates in P3c. P1/P2 single-user has no security surface beyond .env hygiene. This section is a placeholder for a deeper security design doc to be written before P3c kickoff.

P3c MVP: libsodium with master key in env, master key backed up offline (paper + vault). Migration to Vault before public open beta if user count > 20.

Key rotation

  • Master key: rotate every 90 days; re-encrypt all custodial PKs under new master
  • Per-user wallet PK: never (stable identity = stable address)
  • API auth tokens (Mini App ↔ ora2-api): JWT with 24h expiry
  • Telegram bot token: rotate annually or on suspicion

Audit log requirements

  • audit_log table: append-only (no UPDATE/DELETE permission to app role)
  • Every signing op: timestamp, user_id, wallet, action, payload hash
  • Every withdrawal init/confirm/cancel
  • Every admin action (kill switch, force close, balance correction)
  • Replicate to cold storage (Hetzner Object Storage / Backblaze B2) hourly
  • Retention: minimum 7 years (regulatory anchor)

Withdrawal 2FA flow

1. User initiates withdrawal in Mini App
2. ora2-api creates pending withdrawal, generates confirmation_id
3. ora2-bot sends Telegram DM:
   "Confirm withdrawal of $X to 0x... (60s expiry)
    [✓ Confirm] [✗ Cancel]"
4. User taps Confirm in Telegram (signs with their TG identity)
5. ora2-api verifies BOTH:
   - Mini App initiated this confirmation_id
   - Telegram callback came from same user_id within 60s
6. If both yes → execute on-chain withdrawal
7. If timeout / cancel / mismatch → reject + audit_log entry

Breach response plan

  • Immediate: KILL_SWITCH global → halt all trading + freeze all positions
  • <1h: master key rotation → re-encrypt all custodial PKs
  • <4h: pre-drafted incident comms via Telegram bot to all users
  • <24h: postmortem + remediation timeline
  • Insurance: 0 in P3c (too small initially); reconsider at >100 users / >$100k AUM

13Backtest infrastructure NEW

Strategy validation is impossible without replay. Especially critical before SportsScoreReactor (P1.5) and SportsPreEventStrategy (P4) — these are new alpha sources we must validate offline before LIVE.

P1 — capture only

  • All inbound WS events appended to capture_logs (Postgres or local jsonl) with ts and source
  • All /book snapshots polled at decision-tick (3-5s TTL cache exposes them anyway)
  • All /positions snapshots at decision time
  • All Decisions made by Strategy.evaluate (input + output)
  • All ExitIntents from decide_exit (input + output + gates)
  • All order placement attempts + responses + fills
  • Storage: ~500MB/month at expected volume. Rotate to cold storage monthly.

P2 — replay engine

  • Read capture log → simulate WS feed → run through Strategy.evaluate
  • Compare reproducible outputs vs production decisions (regression detection)
  • Useful for: tuning thresholds before LIVE, validating new strategies, post-incident replay
  • Built into vitest test suite as integration tests with fixtures

P3+ — strategy validation harness

  • Fixed period replay (e.g., last 30 days)
  • Threshold sweep (grid search across TP / SL / trailing parameters)
  • Output: per-variant Sharpe ratio, max drawdown, win-rate, total $ pnl
  • Integrate with calibrator (P3+) — automated tuning via Bayesian optimization
